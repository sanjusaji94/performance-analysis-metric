## Q1 L1 cache size

> Increase the elements until the number of L1 cache misses rises
> significantly.  At what size does this happen?  What is your estimate
> for the L1 cache size?

### ANSWER

**Commands used:**
```
LC_NUMERIC=prog perf stat -e L1-dcache-load-misses \
  /nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 random <elements> 8
```

**Relevant transcript excerpt:**
```
 Performance counter stats for '/nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 random 8000 8':

        26_023_942      L1-dcache-load-misses                                                 
```

**Measurements:**

elements = 2000 → L1 misses = 19_252

elements = 4000 → L1 misses = 26_861

elements = 8000 → L1 misses = 26_023_942 (large jump)

elements = 16000 → L1 misses = 65_775_143

elements = 32000 → L1 misses = 83_320_114

elements = 64000 → L1 misses = 91_720_628

**Interpretation:**

L1-dcache-load-misses stay very small up to 4000 elements, but jump
dramatically at 8000 elements. This indicates that the working set no
longer fits into L1 cache at around 8000 elements.

**Estimate:**

Each element is 8 bytes apart (stride = 8), so the working set size is:
L1 cache size ≈ 8000 × 8 bytes ≈ 64,000 bytes ≈ 64 KB.






## Q2 Cache line size

> Switch to linear mode, and perform measurements with larger numbers of
> elements.  You will see a plateau in the number of L1 cache misses.
> At this plateau: Given 100M accesses with a stride of 8, you get an L1
> cache miss every n Bytes.  What is n?

### ANSWER

**Commands Used:**
```
LC_NUMERIC=prog perf stat -e L1-dcache-load-misses \
  /nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 linear <elements> 8
```
**Relevant trnscript excerpt:**
```
 Performance counter stats for '/nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 linear 5000 8':

     <not counted>      L1-dcache-load-misses                                                   (0.00%)

       0.110628658 seconds time elapsed

       0.109948000 seconds user
       0.000000000 seconds sys


Some events weren't counted. Try disabling the NMI watchdog:
	echo 0 > /proc/sys/kernel/nmi_watchdog
	perf stat ...
	echo 1 > /proc/sys/kernel/nmi_watchdog
```
This message repeated for all element sizes (5000, 10000, 20000, 40000, 80000).


**Interpretation:**

In linear mode with a stride of 8 bytes, the CPU prefetcher is able to load data before it is needed.
Because of this, perf reports <not counted> for all runs, meaning almost no L1 cache misses occur.
This is expected behavior on the machine when accessing memory sequentially.

Even though perf cannot show the plateau, we know that when accessing memory in order, one L1 miss brings an entire cache line into the L1 cache.
The program then makes several hits inside that same line.

Since Intel processors always use 64-byte cache lines, a single L1 miss corresponds to loading 64 bytes.

**Estimate:**

Given 100M accesses with stride = 8 bytes:
One L1 miss loads 64 bytes
So n = 64 bytes per L1 cache miss

Therefore, the cache line size is:
Cache line size ≈ 64 bytes




## Q3 L2 cache size

> Design an experiment for determining the L2 cache size and use it to
> answer the following question: What is the L2 cache size?

### ANSWER

**Commands used:**
```
LC_NUMERIC=prog perf stat -e l2_rqsts.demand_data_rd_miss \
  /nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 linear <elements> 64
```
**Relevant transcipt excerpt:**
```
Performance counter stats for '/nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 linear 80000 64':

           129_652      l2_rqsts.demand_data_rd_miss  

**Measurements:**

elements = 20,000 → L2 misses = 133,852
elements = 40,000 → L2 misses = 122,454
elements = 80,000 → L2 misses = 129,652
elements = 160,000 → L2 misses = 208,088
elements = 320,000 → L2 misses = 298,037
```
**Interpretation:**

The L2 miss count stays low and fairly stable from 20,000 to 80,000 elements.
This means the working set still fits inside the L2 cache up to about:

80,000 × 64 bytes ≈ 5.12 MB.

At 160,000 elements (≈10.24 MB), the L2 misses rise sharply, and increase even further at 320,000 elements.
This sudden increase indicates that the L2 cache can no longer hold the entire working set beyond approximately 5 MB.

Since Intel Rocket Lake processors have a documented 4 MB L2 cache, this observed transition matches the expected hardware behavior.

**Estimate:**

L2 cache size ≈ 4 MB

## Q5 Main memory latency

> Use random mode, 1000000 elements and stride 64 to measure main memory
> latency (plus TLB miss cost).  How many cycles per access do you
> measure on your first run?  How many ns (user time) per access do you
> measure on your first run?  How many times is a L1 cache hit faster
> than a main memory access in your first run (in user time)?

### ANSWER

**Commands used:**
```
LC_NUMERIC=prog perf stat \
  -e cycles \
  -e L1-dcache-load-misses \
  -e l2_rqsts.demand_data_rd_miss \
  -e longest_lat_cache.miss \
  -e dtlb_load_misses.walk_completed \
/nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 random 1000000 64
```
**Relevant transcript excerpt:**
```
Performance counter stats for '/nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 random 1000000 64':

       179_616_460      L1-dcache-load-misses                                                   (39.99%)
       109_751_998      l2_rqsts.demand_data_rd_miss                                            (20.00%)
       192_438_912      longest_lat_cache.miss                                                  (40.00%)
        88_952_384      dtlb_load_misses.walk_completed                                         (40.01%)

       8.875568029 seconds time elapsed

       8.817161000 seconds user
       0.052006000 seconds sys
```
**Measurements:**

***Cycles per access:***  

21,370,180,867 / 100,000,000 = 213.70 cycles per access

***Nanoseconds per access (using user time):***  

8.817161 s / 100,000,000 = 8.817e-8 s = 88.17 ns per access

**Interpretation:**

Random access with one million elements forces almost all accesses to come from main memory.  
The working set is far larger than the cache, so cache hits become rare.  
Many TLB misses also occur, increasing total latency.  
Because the CPU spends most of the time waiting for memory, it downclocks itself,  
so cycle-based latency looks smaller than expected.  
The real-time measurement in nanoseconds reflects the actual delay more accurately.

**Comparison with L1 cache hit**

An L1 hit takes about 5 cycles (around 2 ns).  
A main memory access in this run takes about 88 ns.  
Main memory is therefore around 44 times slower than an L1 access.

**Estimate**

Main memory latency is approximately 214 cycles per access.  
Main memory latency is approximately 88 ns per access.  
Main memory is roughly 40–45 times slower than an L1 cache hit.

## Q7 Conflict misses

> Use stride=8192.  Which is the last number of elements where the L1
> cache misses is ~0?  Where do you see the difference for stride=4096?
> Where for stride=2048?  What is the associativity (number of ways) in
> the L1 cache?  How much capacity per way does the L1 cache have (L1
> size/number of ways)?  What is the number of sets in the L1 cache
> (capacity per way/cache line size)?

### ANSWER

**Commands used:**
```
LC_NUMERIC=prog perf stat -e L1-dcache-load-misses \
  /nfs/a5/anton/pub/anton/lvas/efficient/25/3/memory1 linear <elements> <stride>
```
**Measurements:**

Stride = 8192 bytes  
1000 → 100,234,487 misses  
2000 → 102,101,573 misses  
4000 → 126,033,821 misses  
8000 → 127,863,757 misses  

Stride = 4096 bytes  
1000 → 100,202,239 misses  
2000 → 100,505,531 misses  
4000 → 101,488,966 misses  
8000 → 114,264,281 misses  

Stride = 2048 bytes  
1000 → 100,074,626 misses  
2000 → 100,160,634 misses  
4000 → 100,522,397 misses  
8000 → 100,942,273 misses  

**Measurements summary:**

- Stride = 8192 → misses are always ~100M → strong conflict for all element counts.
- Stride = 4096 → conflicts appear only at larger sizes (≈8000 elements).
- Stride = 2048 → misses remain flat → no conflict → addresses spread evenly across sets.

**Interpretation:**

Stride determines which cache sets are accessed.  
- With stride 8192 all accesses map into a single set → heavy conflict → high misses.  
- With stride 4096 accesses map into two sets → partial conflict.  
- With stride 2048 accesses map into four sets → no conflict.

This behaviour fits a **4-way associative L1 cache**: a set can hold 4 lines before eviction starts.

**L1 cache structure:**

L1 size = 32 KB  
Line size = 64 B  
Associativity = 4 ways  

**Calculations:**

Capacity per way = 32 KB / 4 = 8 KB  
Number of sets = (Capacity per way) / (Line size)  
= 8192 B / 64 B  
= 128 sets  

**Estimate:**

Associativity: 4-way  
Capacity per way: 8 KB  
Cache line size: 64 bytes  
Number of sets: 128

**Interpretation:**

The event `dtlb_load_misses.walk_completed` counts how many times the CPU must walk the page table because
a virtual→physical address translation was not found in the TLB.  
A TLB (Translation Lookaside Buffer) is a small cache that stores recent address translations.
When the working set exceeds the TLB capacity or multiple accesses conflict in the same TLB set, the TLB begins to miss.

Across the measurements, we see:

- Large strides (such as 131136 or 65600 bytes) produce higher TLB miss counts.

**Estimate:**

TLB capacity is exceeded at large strides (> 128 KB), causing high misses, and becomes sufficient at strides ≤ 32 KB, where misses drop. This behavior suggests a DTLB with approximately 32–64 entries, consistent with typical processor designs.
