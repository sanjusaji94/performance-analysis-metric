## Q2 What obstructs vectorization?

> What change prevents auto-vectorization by gcc?

I modified dp2.c to introduce a loop-carried dependency by updating x[i]
using x[i-1] inside the loop. Because each iteration depends on the
previous iteration’s result, the loop cannot be safely vectorized with SIMD.
The loop starts at i=1 to avoid accessing x[-1] at i=0.

#### Change in code :
```
--- dp1.c	2025-12-11 19:45:18.000000000 +0100
+++ dp2.c	2026-01-06 12:09:31.772507619 +0100
@@ -3,6 +3,8 @@
 void axpy1(float a, float *x, float * restrict y, size_t n)
 {
   size_t i;
-  for (i=0; i<n; i++)
-    y[i] += a*x[i];
-}
+  for (i=1; i<n; i++) {
+    x[i] = x[i - 1] * (float)n;   // loop-carried dependency
+    y[i] += a * x[i];
+  }

```
#### Measurement after the code update :
```
Performance counter stats for './dp2-noauto-gcc':

        4438404005      cycles:u                                                              

       0.951863104 seconds time elapsed

       0.939794000 seconds user
       0.011997000 seconds sys

 Performance counter stats for './dp2-auto-gcc':

        4439271440      cycles:u                                                              

       0.951015818 seconds time elapsed

       0.947069000 seconds user
       0.003996000 seconds sys
```
To determine whether auto-vectorization works, I compare the speedup
(measured in cycles:u) of dp2-auto-gcc over dp2-noauto-gcc.
Auto-vectorization is considered unsuccessful if the speedup is not more
than 1.5×, i.e. cycles(noauto) / cycles(auto) ≤ 1.5.

Measured cycles:u (gcc):

dp2-noauto-gcc: 4,438,404,005
dp2-auto-gcc:   4,439,271,440

Speedup = cycles(noauto) / cycles(auto)
        = 4,438,404,005 / 4,439,271,440
        ≈ 0.9998× (≤ 1.5×)

Therefore, gcc auto-vectorization does not work for the modified dp2.c.


> What change prevents auto-vectorization by clang?

To prevent auto-vectorization by clang with a minimal change, I disabled
loop vectorization explicitly by inserting the clang loop pragma
`#pragma clang loop vectorize(disable)` directly before the loop in
`axpy1()` (guarded by `#ifdef __clang__`).

#### Change in code :

```
--- dp1.c	2025-12-11 19:45:18.000000000 +0100
+++ dp3.c	2026-01-06 21:34:25.318478269 +0100
@@ -3,6 +3,10 @@
 void axpy1(float a, float *x, float * restrict y, size_t n)
 {
   size_t i;
+  
+#ifdef __clang__
+#pragma clang loop vectorize(disable)
+#endif
   for (i=0; i<n; i++)
     y[i] += a*x[i];
 }

For clang, auto-vectorization was disabled explicitly using a clang-specific
loop pragma, ensuring that the compiler does not vectorize the loop even in
the auto variant.

```
#### Measurement after the code update :


## Q3 When does gcc auto-vectorization fail?

> Please show a vectorizable loop (extracted from `dp4.c`) that is
vectorizable (equivalent manually vectorized code in `dp4-manual.c`),
but that gcc does not auto-vectorize.  Include the measurements that
indicate that the non-vectorization of `dp4-auto-gcc` and the
vectorization of `dp4-manual-gcc`.

The original loop in dp4.c is vectorizable and gcc successfully
auto-vectorizes it. This is visible because dp4-auto-gcc is much faster
than dp4-noauto-gcc, and its performance is similar to the manually
vectorized version dp4-manual-gcc.

To create a case where the loop is still vectorizable but gcc does not
auto-vectorize it, I inserted a compiler memory barrier inside the loop:
asm volatile("" ::: "memory"); . This forces gcc to assume memory may
change in an unknown way between iterations and prevents auto-vectorization.

#### Code Change 

```
--- dp1.c	2025-12-11 19:45:18.000000000 +0100
+++ dp4.c	2026-01-06 22:49:17.325296913 +0100
@@ -3,6 +3,8 @@
 void axpy1(float a, float *x, float * restrict y, size_t n)
 {
   size_t i;
-  for (i=0; i<n; i++)
+  for (i=0; i<n; i++){
+    asm volatile("" ::: "memory");   // blocks auto-vectorization
     y[i] += a*x[i];
-}
+  }
+}
```
